## Objective

Initialize Alembic against the SQLAlchemy `Base` from T010. Generate the initial migration (`0001_initial.py`) containing every table, index, constraint, and FK from `data-model.md`. Add a second migration (`0002_seed_defaults.py`) that inserts the `global_settings` row with id=1 and sensible defaults. Wire both to run automatically on control-plane container startup.

## Context

Schema changes go through Alembic. The initial migration is generated via `--autogenerate` but **must be hand-reviewed** before commit — autogeneration is sloppy with partial indexes, CHECK constraints with `IN` clauses, ARRAY columns, and some JSONB defaults. Migrations live in `backend/migrations/versions/`. On every container start, the entrypoint runs `alembic upgrade head` before launching the API — this means model changes can ship without operator intervention.

## Steps

1. **Initialize Alembic** from `backend/`:
   ```
   uv run alembic init --template async migrations
   ```
   This generates `alembic.ini`, `migrations/env.py`, `migrations/script.py.mako`, `migrations/versions/`.

2. **Edit `alembic.ini`** — remove the `sqlalchemy.url` value (it'll be set in `env.py` from Settings) but keep the line as a blank. Set `script_location = migrations`.

3. **Edit `migrations/env.py`** to:
   - Import `Settings` and the metadata: `from krelix.config import get_settings; from krelix.models.base import Base`.
   - Set `target_metadata = Base.metadata`.
   - In the async `run_migrations_online`, set `connection.execute(text("..."))` only as needed; the default Alembic async template is mostly fine.
   - Replace `config.set_main_option("sqlalchemy.url", ...)` with `get_settings().database_url`.

4. **Generate the initial migration:**
   ```
   uv run alembic revision --autogenerate -m "initial schema"
   ```
   Rename the generated file to `0001_initial.py`. Commit the autogenerated file untouched first, then audit:

5. **Hand-review `0001_initial.py`** against `data-model.md`. Specifically check:
   - Every table from `data-model.md` is present
   - Every column with the right type and nullability
   - Every CheckConstraint (`status IN (...)` etc.) is included — **autogenerate often misses these**; add manually with `sa.CheckConstraint("status IN ('pending','provisioning',...)", name="ck_deployment_status_valid")`.
   - The `global_settings` single-row CheckConstraint (`id = 1`)
   - The `huggingface_credential` single-row CheckConstraint (`id = 1`)
   - ARRAY columns (`deployment.gpu_indices`) — autogenerate may produce `JSON` instead; fix to `postgresql.ARRAY(sa.Integer)`.
   - JSONB columns — verify they use `postgresql.JSONB` not `JSON`
   - Indexes from `data-model.md`: `(endpoint_id, last_used_at)`, `(endpoint_id, in_hot_tier)`, `(endpoint_id, status)`, `initiated_at DESC`, `(deployment_id, event_at DESC)`, `parent_nvml_uuid`, GIN on `model.hf_metadata`.
   - Partial unique index on `endpoint.hostname` where `deleted_at IS NULL` (and `vault.name` similarly) — autogenerate misses these. Add manually:
     ```python
     op.create_index(
         "uq_endpoint_hostname_active", "endpoint", ["hostname"],
         unique=True, postgresql_where=sa.text("deleted_at IS NULL"),
     )
     ```
   - FK ON DELETE behavior matches the spec.

6. **Write `0002_seed_defaults.py`** — a data migration:
   ```python
   from alembic import op

   revision = "0002"
   down_revision = "0001"
   branch_labels = None
   depends_on = None

   def upgrade() -> None:
       op.execute("""
           INSERT INTO global_settings (id, default_hot_tier_path, default_vault_id,
               eviction_policy_type, eviction_threshold, auto_iteration_retry_budget, updated_at)
           VALUES (1, '/var/lib/krelix/hot', NULL,
               'percent_free', 15.0, 5, now())
           ON CONFLICT (id) DO NOTHING
       """)

   def downgrade() -> None:
       op.execute("DELETE FROM global_settings WHERE id = 1")
   ```

7. **Write `backend/scripts/entrypoint.sh`:**
   ```sh
   #!/bin/sh
   set -e
   echo "Running migrations..."
   alembic upgrade head
   echo "Migrations done. Starting command: $@"
   exec "$@"
   ```
   Make it executable: `chmod +x backend/scripts/entrypoint.sh`.

8. **Update `backend/Dockerfile`:**
   - Copy `scripts/entrypoint.sh` into the runtime image at `/app/scripts/entrypoint.sh` (with executable bit).
   - Add `ENTRYPOINT ["/app/scripts/entrypoint.sh"]` before the existing `CMD`.
   - Keep `CMD ["krelix-api"]` — the entrypoint runs migrations then execs whatever the CMD is, so `docker run krelix-control:dev krelix-worker` still works correctly (worker also waits for migrations to apply, which is safe).

9. **Write `backend/tests/test_migrations.py`** as an integration test:
   - Against a clean test DB (use a dedicated DB name like `krelix_test`), assert `alembic upgrade head` runs without error.
   - Assert all expected tables exist via `inspect(engine).get_table_names()`.
   - Assert the seed row exists: `SELECT * FROM global_settings WHERE id = 1` returns one row with the expected defaults.
   - Assert `alembic downgrade base` undoes everything (or document why downgrade is not supported for some migrations).

10. **Verify:**
    - From `backend/`: `uv run alembic upgrade head` against the dev DB succeeds and creates all tables.
    - `psql` into the dev DB and confirm: `\dt` lists all 11 tables; `SELECT * FROM global_settings;` returns one row.
    - `make test` (with integration enabled) green.
    - Build the Docker image; `docker run --env-file .env krelix-control:dev` runs migrations on startup before serving.

## Notes

- The async Alembic template is more involved than sync. If you hit edges with the template, falling back to a synchronous Alembic env (using `psycopg2` or `psycopg` for migrations only) is acceptable — Alembic doesn't need async for any practical reason. Async sessions are for the running app, not for the migration tool. Surface this choice if you make it.
- Hand-reviewing the autogenerated migration is mandatory. Don't blindly commit what `--autogenerate` produced; it routinely misses CheckConstraints, partial indexes, and ARRAY types.
- Migration filenames use the `0001` / `0002` prefix instead of Alembic's default UUID prefix — set `file_template = %%(rev)s_%%(slug)s` in `alembic.ini` to get this. Or live with the UUID prefix and just rename — but consistency matters.
